This is a temporary, profile-only identity verification process, not a backend enrollment mode. It has no database, health API, refresh grant, automatic allowlist update, or durable result/token store. Source preparation does not authorize WHOOP consent or deployment.

Run it only for the owner's newly created WHOOP app before its real backend grant exists. Revoking the temporary grant revokes that user's access for this app; do not use this process against an app with another connection that must remain active. Obtain explicit user authorization for the profile-only consent step first. The operator must already have the exact registered private HTTPS callback, `https://<approved-backend-hostname>/whoop/callback`, and the existing dedicated enrolled backend node. This process cannot enroll a node or create public ingress.

The one-time private `/data/config/identity.json` has exactly `mode: "whoop-owner-identity"`, `hostname`, `clientId`, and `clientSecret`. The file must be UID1000-owned, single-link, mode0600, in the private UID1000-owned mode0700 config directory. Keep the app secret in the approved secret store and inject it through a separately reviewed private provisioning step. Never use command arguments, URLs, chat, logs, screenshots or Git for credentials. This directory must not contain backend database, health tokens or other app secrets. The enrolled Tailscale state remains a separate private directory; existing exclusive ownership checks prevent a second service from using it concurrently.

For a separately approved run, temporarily stop the existing service on that exact backend node and launch only this artifact with no restart policy. Its fixed HTTP listener is 127.0.0.1:8080 behind the existing verified Tailscale HTTPS Serve configuration. No public domain or port is needed. The image must retain the reviewed non-root/NNP, resource, TLS and network controls; allow outbound WHOOP HTTPS only as required by the separately reviewed execution environment. Its fixed entrypoint must clear the environment before Node starts; an in-process environment check cannot undo pre-main Node/OpenSSL configuration. The process accepts no enrollment flag or arbitrary target. Packaging, secret provisioning and deployment are separate gates; they have not been done by writing these files.

The owner opens that private origin in their own browser, starts the five-minute flow, and consents to `read:profile` only. The request omits health and `offline` scopes. The callback binds random state, S256 PKCE and a Secure/HttpOnly/SameSite cookie to the same browser. The process makes one bounded profile request and displays only the returned name/email as escaped text for human confirmation. After confirmation, it revokes the temporary grant and only then displays the numeric ID. Cancel, expiry, malformed data or failed revocation never produce an approved ID. This is a single-browser flow; an unexpected browser occupying it requires an operator restart, not relaxing the binding.

The final operator must bind the exact displayed ID to the actual owner's explicit account confirmation before writing `ALLOWED_WHOOP_USER_ID` through the approved private backend configuration process. A different supplied ID, a client/team/device identifier, or the first production callback is not an acceptable substitute. This utility never writes that setting. Keep the backend's existing exact numeric allowlist checks unchanged.

If consent was granted but the process fails or is killed, revoke the app connection in WHOOP before retrying. A lost token response or hard process termination can prevent programmatic revocation; no in-process cleanup can guarantee otherwise. The process requests no refresh token and never persists one. A successful final page proves that this run received the documented revocation success response, not that unrelated copies or provider records have been erased. Restore the reviewed normal service afterward and remove the temporary identity config. The real health-data OAuth consent remains a separate step.
