This is a preparation package for one fresh, dedicated private PostgreSQL database. No real database has been deployed, initialized or given credentials. The immutable base is the already acquired official AMD64 PostgreSQL 17.11 bookworm image, `postgres@sha256:66aafa11cf15800a3c94763f7e11d1e7b2e37e5e84bc4ce027cb6e1e4bfaf4df`. The Dockerfile adds only public configuration/SQL templates, installs nothing, runs as UID/GID 999 with no-new-privileges and a cleared child environment, and bypasses the vendor initialization entrypoint. Missing initialized data, TLS material or rendered configuration stops startup. The exact built image and exercised synthetic checks are recorded in [VALIDATION.md](VALIDATION.md); live/provider and remaining provisioning checks are still gates.

The pinned base has unresolved image advisories; its digest is reproducibility evidence, not a claim that it is free of vulnerabilities. [The image security review](../../IMAGE_SECURITY_REVIEW.md) records the scan and reachability limits, including SQL/XML exposure after runtime-credential compromise. The operator's accepted residual-risk category does not remediate those findings.

The intended topology is one PostgreSQL service and one persistent volume in the separately approved personal Railway environment, reachable by the real backend and a temporary migration job through Railway private networking. There is no Tailscale node in this database service, no public domain, no TCP proxy and no published host port. The existing synthetic staging gateway/fixture is separate. Railway project administrators and the database container's OS administrator retain access to the data; PostgreSQL roles do not isolate against them. The database contains WHOOP credentials and application authentication state, so its volume, backups and operator evidence are private.

Choose the exact assigned `DATABASE_HOST` first: one lowercase service label followed by `.railway.internal`, matching the backend's validated configuration. Render only `@DATABASE_HOST@` in the two templates after validating that name; do not substitute shell expressions or accept names from a remote response. The server binds this hostname's resolved private addresses, rather than all interfaces. Independently verify its actual private address/listener and the absence of public ingress before entering credentials. The HBA rules admit only TLS plus SCRAM for the two named logins on database `whoop`; the administrator has only the private Unix-socket peer route. HBA's IPv4/IPv6 catch-all source ranges are authentication rules, **not per-service network isolation**: another service that can reach this private listener can attempt authentication. [PostgreSQL HBA rules](https://www.postgresql.org/docs/17/auth-pg-hba-conf.html) and [listener configuration](https://www.postgresql.org/docs/17/runtime-config-connection.html) describe those distinct controls.

Issue a server leaf certificate with exactly that DNS SAN using `server-cert.cnf.template`; do not use wildcard, localhost or IP aliases. Keep the CA signing key outside every running database/backend/migration container. Only the database receives the leaf private key; the backend receives the public CA certificate at `/data/config/db-ca.pem`, while the one-off migrator receives the same public trust anchor in its private configuration. Verify the chain, current validity, SAN and key match before startup, and record certificate expiry/renewal ownership. Both clients must verify the certificate and exact hostname. Enabling server TLS alone does not forbid plaintext; the explicit HBA rejections do. [PostgreSQL TLS guidance](https://www.postgresql.org/docs/17/ssl-tcp.html).

Use one dedicated volume mounted at `/var/lib/postgresql/data`, overriding the base image's declared volume so Docker does not create an untracked anonymous volume. Its `pgdata`, `config`, `tls` and `run` directories must be UID/GID 999, mode 0700; private configuration and key files are mode 0600, regular, single-link and not symlinks. `config/postgresql.conf` is the rendered configuration; `tls/server.pem` and `tls/server-key.pem` are the chain and key. The private socket directory is `/var/lib/postgresql/data/run`, initialized on that same dedicated volume; it does not require a provider-specific runtime mount. Supply a bounded `/tmp`. The socket directory is never mounted into the application. Prefer a read-only root, dropped capabilities, bounded memory/PIDs and no host mounts/SSH forwarding. Observe the actual provider controls; this Dockerfile does not enforce Railway resource limits, root-filesystem policy or outbound firewalling. PostgreSQL itself can rewrite its owned volume after a database-process compromise.

The proposed roles are fixed and deliberately separate:

| Role | Authentication and authority |
| --- | --- |
| `whoop_admin` | Bootstrap superuser and database owner; no password, network HBA denied, private OS-peer socket only. An operator with database-container execution authority can use it. |
| `whoop_owner` | NOLOGIN schema/table owner, no global privileged attributes. Temporary CREATE on this database only during migration. |
| `whoop_migrate` | Initially NOLOGIN. One-hour password validity when explicitly enabled; non-inherited SET ROLE membership in `whoop_owner`, no ADMIN OPTION, no global CREATEDB/CREATEROLE. LOGIN/password/membership disabled after the job; the role remains. |
| `whoop_runtime` | Initially NOLOGIN. Enabled only after validation; CONNECT, public-schema USAGE and SELECT/INSERT/UPDATE/DELETE on the six application tables. No membership, schema/database CREATE, TEMP, ledger access, table ownership or grant option. |

The separate `Dockerfile.provision` artifact copies the pinned Node 22 binary into the same PostgreSQL base. It has four explicit, sequential phases; it is not the normal database image. Stop and remove the previous phase container before starting the next one on the same volume, and verify that no other container/service uses that volume. The fixed state marker and exclusive lock reject replay and incomplete phases. They do not replace provider-level single-volume ownership. On success each phase holds inertly with no PostgreSQL process or listener, avoiding automatic restart/re-enrollment. Stop that temporary deployment deliberately; never leave two deployments sharing the database volume.

1. Run `init` as root with **no provisioning variable or stdin secret**, only on the approved empty volume. It creates private directories, clears supplementary groups, drops permanently to UID/GID 999, runs fixed `initdb` with peer-only local authentication and rejected host authentication, and records `initialized`. Existing or partial content is refused. Root is needed only to set volume ownership; minimize its capabilities/duration. The Node process and children receive fixed cleared environments.
2. Run `configure` as UID/GID 999 with the exact bounded JSON envelope: `{version:1,host,caCertificate,serverCertificate,serverKey,runtimePassword,migrationPassword}`. The host is the assigned private hostname; the two passwords must be distinct generated 64-character lowercase hex strings. The helper validates the single CA, current leaf certificate, exact DNS SAN, RSA key match and server-auth purpose before writing private files. It claims the `configuring` state before writes, then uses the fixed local peer socket with `listen_addresses=''` to run `00-provision.sql` and set SCRAM passwords while both roles remain NOLOGIN. No caller SQL is accepted, and plaintext passwords enter `psql` only through stdin. Child output is bounded and replaced by fixed errors. Any failure preserves partial state for inspection, attempts bounded shutdown and retains the ownership lock if termination is unconfirmed; it refuses a blind retry.
3. Run `enable` as UID/GID 999 without a provisioning variable or stdin bytes. It revalidates private files and the exact rendered configuration, starts only the local peer listener, and runs pinned `10-enable-migration.sql`. The migrator receives one hour of LOGIN and temporary SET ROLE authority. Standard Drizzle needs the owner's temporary CREATE on this database; that also permits schemas, publications and trusted extensions until revoked, but is not global CREATEDB and never belongs to the runtime role. The helper stops PostgreSQL before marking `enabled`.
4. Start the normal PostgreSQL image on the same volume and validate its private listener/TLS. Run the separately packaged [one-off migrator](../migrate/README.md) once through its fixed stdin bridge, with only `whoop_migrate`, `whoop_owner`, database `whoop`, exact host and public CA. Keep the backend stopped. Remove the completed migration deployment, then stop the normal database before the next helper phase.
5. Run `finalize` as UID/GID 999 without variable/stdin input. Pinned `20-finalize.sql` first commits removal of migration LOGIN/password/membership/CONNECT and owner database CREATE. After the authentication deadline, it refuses runtime activation if any migration session remains or the exact tables, ownership or three pinned ledger entries differ. A failed validation keeps the revocations committed and leaves the `finalizing` marker; no automatic retry or session killing occurs. Success grants only runtime CRUD and records `finalized`, after stopping the local PostgreSQL process.
6. Remove the preparation deployment and verify its active provisioning variable is absent. Start the normal database, independently validate runtime CRUD and denied operations, then deliver **only** the canonical runtime TLS URI/public CA to the guarded backend, keeping `RUN_MIGRATIONS=false`. The normal PostgreSQL image clears its inherited child environment, but does **not** itself reject a provisioning variable's presence: the operator must verify removal. No real phase is authorized by this source package.

For Railway, the configure-only shell bridge accepts a temporary project/service-scoped `WHOOP_POSTGRES_PROVISION` variable. It verifies real/effective UID/GID 999 and kernel no-new-privileges before accessing the value, then sends it via a builtin `printf` pipe into an environment-cleared Node process. Direct non-TTY stdin remains available in isolated tests. Root init and the other phases reject the variable even if empty. No administrator password, WHOOP credential, gateway token, SSH key or host credential belongs in this envelope. The CA signing key never enters it. Delivering the variable needs explicit operator approval and a private CLI-stdin channel; never put its content in arguments, logs or Git.

This bridge does not erase the temporary shell's original Linux environment, provider variable history, older deployment snapshots or administrators' access. Delete the active variable, remove the temporary deployment and use a fresh normal deployment after the phase. Record retained provider history as exposure; deletion is not assured historical erasure. Future migration, certificate renewal, role re-enablement, restore or populated-volume reuse needs another reviewed procedure. These helpers intentionally offer no recovery/overwrite command.
